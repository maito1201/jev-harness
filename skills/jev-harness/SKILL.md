# jev-harness — 見せる前に自分で検査する

hook は工程と証拠を管理する。差し戻し回数を使い切っても不合格が合格に変わることはない。
実装依頼は `design → premises → implementation → evaluation → execution → results → complete` の順に進む。
計画には合意した目的、前提の検査、小規模な実装検証、評価方法の独立検査、本実行、固定基準による結果確認を含める。
各工程では hook が返す役割・許可操作に従う。工程は宣言では進まず、対応する実際の処理結果で進む。
評価方法の検査では、正しい実装だけでなく意図的に誤った実装を落とせるか確かめる。小規模検証と同一コマンドの再実行は代用にならない。
評価基準を変える場合は設計へ戻り、既存の合格を失効させる。実装失敗・評価不備・前提の反証を区別し、戻された工程から原因を直す。
工程継続の差し戻しはユーザーの新しい要求ではない。元の要求と承認を保持する。
審査不能や原因不明は完了扱いにしない。詳細と制約はプラグインルートの WORKFLOW.md を参照。
審査障害時は `Read` または単独の `Get-Content -LiteralPath 'path'` で診断できる（外部審査不要）。`functions.exec` で包む場合は JSON 引数の `text(await tools.exec_command({"cmd":"Get-Content -LiteralPath 'path'"}));` だけにする。進展のない Stop 差し戻しは3回で未完了として終了し、変更・実行は許可されない。復旧はユーザーの修正指示を受けて再審査する。詳細は RECOVERY.md。
道具は `node "${PLUGIN_ROOT}/bin/jev-check.mjs" <mode>`。stdin に JSON、stdout に JSON、1回 0.2〜0.7 秒。

## いつ使うか

- **方針が2つ以上あるとき** → `rank`。`{"claim": "解くべき主張・依頼", "sketches": {"名前": "方針の要約"}}`。Score 2 に近いものから展開し、0 台は捨てる。一つに決め打ちしない
- **証明・設計・計画の下書きを書いたとき** → `gaps`。`{"claim": "...", "draft": "...", "steps": ["1. ...", "2. ..."]}`。`assumes_conclusion` `handwave` `cases_incomplete` `unproved_lemma` が 0.5 を超えた箇所、`suspect_steps` に出たステップを直す。`establishes_claim` が 0.8 未満なら完了と言わない
- **依頼と関係が薄いファイルを触りそうなとき** → `scope`。`{"request": "...", "files": ["a.ts", "b.ts"]}`。0.8 以上のファイルは触る理由をユーザーに書く

## 判定の限界（信じすぎない）

- jev は文面の判定器で、算術と多段推論はできない。数値・代数の主張は自分でコード（計算・テスト）で確かめる。記事の Gemini は 92,670² を捏造して検算を通した。同じことを自分がしていないか、計算はコードに出す
- `establishes_claim` 0.9 は「穴の型が見えない」であり、正しさの証明ではない。最終判定はテスト・実行結果・人間
- 同じ方針の言い換えは 0.98 で検出するが、部分的に重なる別方針も 0.74 と出る。方針の多様性は自分で担保する
